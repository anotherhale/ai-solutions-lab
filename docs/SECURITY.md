# Security

Security is a first-class concern for every future application in this repository. These principles apply to documentation, synthetic data, local tooling, and later Azure deployments.

No production environment has been deployed. The absence of running services does not relax the rules below.

## Secrets

- Secrets must never be committed.
- `.env` is for local development only and is ignored by Git.
- `.env.example` may contain placeholder names and empty or obviously fake values.
- Cloud deployments, when they exist, must use a managed secret store rather than files in the repository or container images.
- Rotate any credential that is accidentally written to logs, tickets, or chat.

## Environment and Configuration

- Configure local development through environment variables.
- Keep environment-specific values out of application code.
- Do not embed API keys, connection strings, or tenant identifiers in ADRs, case studies, or prompts.

## Authorization

- Implement least-privilege authorization for every actor, service account, and workflow.
- Default deny access to customer, employee, and financial records.
- Separate read paths from paths that can change schedules, invoices, or customer communications.
- Do not give AI tools more authority than the user who invoked them.

## Sensitive Business Information

Wasatch Business Systems data is synthetic, but it must be handled as if it were real SMB data.

- Minimize the fields used in prompts, logs, and embeddings.
- Do not publish synthetic customer or employee records outside the laboratory without a documented reason.
- Redact identifiers before using documents as model-evaluation examples when the full record is unnecessary.

## Audit Trails

Consequential actions require an audit trail. That includes, at minimum:

- Financial postings and invoice changes
- Customer-visible messages
- Dispatch or schedule changes that affect field work
- Permission and approval changes

An audit record should capture actor, action, subject, time, approval identity, and outcome.

## Untrusted Inputs

Treat the following as untrusted:

- External documents
- Email and chat content
- Model outputs
- Tool arguments generated by a model
- Files uploaded for document processing
- Retrieval results that originated from user-supplied documents

Validate structure and policy before a model output can trigger a side effect.

## Human Approval

Require a human approval record before:

- Sending customer-facing communications that commit the business
- Changing prices, invoices, payroll, or payment instructions
- Creating or canceling field work that incurs cost
- Exporting bulk customer or employee information
- Connecting a new external system or expanding tool permissions

Automation may draft, classify, route, and recommend. It may not silently complete those actions.

## Development and Delivery

- GitHub Actions workflows must not require cloud credentials or API keys for foundation validation.
- Dependencies are added only with a stated purpose and are reviewed for maintenance and license risk.
- Observability must avoid recording secrets or raw regulated content.
- Security reviews are required when a change expands data access, tool use, or network egress.
